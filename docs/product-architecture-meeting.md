# 产品架构重构会议纪要

**时间：** 2026-05-01 晚上  
**参会人员：** 项目产品（40%）、技术产品（30%）、业务产品（30%）  
**议题：** 基于第四次评审结果，重新架构产品体系

---

## 📋 会议背景

**第四次评审结果：**
- 综合得分：5.94/10 ❌ 不通过
- 核心问题：缺少财务合规模块（往来账、结账、税务）+ 业务完整性不足（合同、库存）
- 要求：新增 3 个领域上下文（Finance/Contract/Inventory）

**产品困境：**
- 原定位：轻量级利润决策系统（MVP 4周）
- 新需求：完整的财务业务一体化系统（复杂度 10倍）
- 矛盾：如何平衡"快速上线"和"功能完整"？

## 🎨 项目产品视角（40% 权重）

### 核心观点：分阶段交付，而非一次性交付

**问题诊断：**
```
当前设计的根本问题：
❌ 试图在一个系统里解决所有问题
❌ MVP 范围失控（从 5 个模块扩展到 10+ 个模块）
❌ 没有明确的产品边界

结果：
- 开发周期从 4 周变成 6 个月
- 风险巨大（做了半年发现不对）
- 用户等不及
```

### 解决方案：产品分层架构

```
┌─────────────────────────────────────────┐
│         Layer 3: 决策智能层              │
│   （AI 决策、预测分析、智能推荐）         │
│            【未来规划】                  │
└─────────────────────────────────────────┘
              ↑
┌─────────────────────────────────────────┐
│         Layer 2: 管理会计层              │
│   （成本归因、利润分析、预算管理）        │
│         【第二阶段 - 3个月】             │
└─────────────────────────────────────────┘
              ↑
┌─────────────────────────────────────────┐
│         Layer 1: 财务核算层              │
│   （收支记录、往来账、结账、税务）        │
│         【第一阶段 - 2个月】             │
└─────────────────────────────────────────┘
```

### 产品路线图（Roadmap）

#### 🎯 Phase 1: 财务核算系统（2个月）

**目标用户：** 财务人员  
**核心价值：** 替代 Excel，规范财务记账

**功能范围：**
```
✅ 必须有（P0）：
1. 收支记录（收入/成本录入）
2. 会计科目（标准科目表）
3. 应收应付管理
4. 期间结账
5. 基础报表（收支明细、应收应付表）

✅ 应该有（P1）：
6. 发票管理
7. 税务申报（增值税）
8. 银行对账

❌ 暂不做：
- 成本归因（留给 Phase 2）
- 预算管理（留给 Phase 2）
- 决策建议（留给 Phase 3）
- 合同管理（留给 Phase 2）
- 库存管理（留给 Phase 2）
```

**验收标准：**
- 财务人员可以完整记录一个月的收支
- 可以生成标准的收支明细表
- 可以完成月度结账
- 数据准确性 100%

**技术债务：**
- 预留归因接口（为 Phase 2 做准备）
- 预留多维度字段（org_unit/project/counterparty）

---

#### 🎯 Phase 2: 管理会计系统（3个月）

**目标用户：** 财务人员 + 部门经理 + 高层  
**核心价值：** 知道钱花在哪里、赚在哪里

**功能范围：**
```
✅ 必须有（P0）：
1. 成本归因（基于 Phase 1 的数据）
2. 多维度分析（部门/项目/客户）
3. 利润核算（按组织/项目）
4. 预算管理（编制/执行/对比）
5. 经营看板

✅ 应该有（P1）：
6. 合同管理（收入确认依据）
7. 项目核算
8. 客户分析

❌ 暂不做：
- 库存管理（制造业专属，可选模块）
- 固定资产（可选模块）
- 工时管理（可选模块）
```

**验收标准：**
- 可以查看各部门的利润贡献
- 可以对比预算 vs 实际
- 可以分析客户贡献

---

#### 🎯 Phase 3: 决策智能系统（未来）

**目标用户：** 高层管理者  
**核心价值：** 告诉我该做什么

**功能范围：**
```
1. 问题自动识别
2. 根因分析
3. 决策建议生成
4. 执行效果跟踪
5. AI 预测（可选）
```

### 产品定位调整

```
旧定位：
"利润决策系统"
→ 用户期望：AI 自动决策
→ 实际：只是数据记录 + 简单分析
→ 落差大

新定位：
Phase 1: "财务记账系统"（明确、实用）
Phase 2: "经营分析系统"（有价值）
Phase 3: "智能决策系统"（有想象空间）
```

## 💻 技术产品视角（30% 权重）

### 核心观点：技术架构支持分阶段演进

**技术挑战：**
```
问题：
- Phase 1 只做记账，Phase 2 要做归因
- 如何避免 Phase 2 推翻 Phase 1 的设计？

风险：
- Phase 1 设计太简单 → Phase 2 重构成本高
- Phase 1 设计太复杂 → Phase 1 交付延期
```

### 解决方案：领域驱动 + 微服务架构

#### 架构分层

```
┌─────────────────────────────────────────┐
│          前端层（Vue3）                  │
│  Phase 1: 记账页面                       │
│  Phase 2: 分析页面                       │
│  Phase 3: 决策页面                       │
└─────────────────────────────────────────┘
              ↓ API Gateway
┌─────────────────────────────────────────┐
│          应用层（Spring Boot）           │
│  Phase 1: FactService                   │
│  Phase 2: AttributionService            │
│  Phase 3: DecisionService               │
└─────────────────────────────────────────┘
              ↓
┌─────────────────────────────────────────┐
│          领域层（DDD）                   │
│  Phase 1: Fact + Finance Context        │
│  Phase 2: Attribution + Metrics Context │
│  Phase 3: Decision Context              │
└─────────────────────────────────────────┘
              ↓
┌─────────────────────────────────────────┐
│          基础设施层                      │
│  MySQL + Redis + RabbitMQ               │
└─────────────────────────────────────────┘
```

#### 数据库设计策略

**Phase 1 表结构（核心）：**
```sql
-- 事实表（完整设计，但部分字段暂不使用）
fact_event
├── id
├── business_date / accounting_date  ✅ Phase 1 使用
├── type / amount                    ✅ Phase 1 使用
├── account_code                     ✅ Phase 1 使用
├── counterparty_id                  ✅ Phase 1 使用
├── org_unit_id                      ⚠️ Phase 1 记录，Phase 2 使用
├── project_id                       ⚠️ Phase 1 记录，Phase 2 使用
├── cost_category                    ⚠️ Phase 1 记录，Phase 2 使用
└── ...

-- 财务表（Phase 1 核心）
receivable / payable                 ✅ Phase 1 使用
period_closing                       ✅ Phase 1 使用
accounting_subject                   ✅ Phase 1 使用

-- 归因表（Phase 2 才用）
attribution                          ❌ Phase 1 不创建
attribution_rule                     ❌ Phase 1 不创建

-- 指标表（Phase 2 才用）
metric_snapshot                      ❌ Phase 1 不创建
```

**策略：**
- Phase 1：创建完整的 fact_event 表，但只使用财务相关字段
- Phase 2：启用归因相关字段，创建 attribution 表
- 优点：避免 Phase 2 修改表结构（只是启用字段）

#### API 设计策略

**Phase 1 API（财务核算）：**
```
POST /api/v1/facts              # 录入收支
GET  /api/v1/facts              # 查询收支
POST /api/v1/receivables        # 应收管理
POST /api/v1/period-closing     # 期间结账
GET  /api/v1/reports/income     # 收支报表
```

**Phase 2 API（管理会计）：**
```
GET  /api/v1/attributions       # 归因查询
GET  /api/v1/metrics            # 指标查询
GET  /api/v1/budgets            # 预算管理
GET  /api/v1/projects/profit    # 项目盈亏
```

**Phase 3 API（决策智能）：**
```
GET  /api/v1/decisions          # 决策建议
POST /api/v1/actions            # 执行记录
```

**策略：**
- API 版本化（/v1/v2）
- Phase 1 API 在 Phase 2 保持兼容
- 新功能用新 API

## 👔 业务产品视角（30% 权重）

### 核心观点：业务场景驱动功能优先级

**问题诊断：**
```
当前设计的问题：
❌ 功能列表式设计（有什么功能）
✅ 应该：场景驱动设计（解决什么问题）

例如：
❌ "库存管理"是功能
✅ "制造业成本核算"是场景
   → 需要库存管理
   → 需要工时管理
   → 需要生产工单
```

### 业务场景分类

#### 🏢 场景1：贸易/服务业（80% 企业）

**业务特点：**
- 无库存（或库存简单）
- 成本主要是人力 + 采购
- 收入确认简单

**Phase 1 需求：**
```
✅ 收入录入（开票即确认）
✅ 成本录入（采购/人力）
✅ 应收应付管理
✅ 期间结账
```

**Phase 2 需求：**
```
✅ 按部门归因
✅ 按项目归因
✅ 按客户分析
✅ 预算管理
```

**不需要：**
❌ 库存管理
❌ 生产工单
❌ 工时管理（可选）

---

#### 🏭 场景2：制造业（20% 企业）

**业务特点：**
- 有库存（原材料/半成品/产成品）
- 成本复杂（料工费）
- 收入确认复杂（按生产进度）

**Phase 1 需求：**
```
✅ 收入录入
✅ 采购入库（不计成本）
✅ 应收应付管理
✅ 期间结账
```

**Phase 2 需求：**
```
✅ 库存管理 ★
✅ 生产领料（计入成本）★
✅ 工时管理 ★
✅ 按产品归因
✅ 按工单归因
```

**特殊需求：**
- 成本核算方法（先进先出/加权平均）
- 在产品成本分摊

---

### 产品策略：主线 + 可选模块

```
主线产品（贸易/服务业）：
Phase 1: 财务核算 ✅
Phase 2: 经营分析 ✅

可选模块（制造业）：
- 库存管理模块
- 生产管理模块
- 工时管理模块

策略：
- 主线产品先做（覆盖 80% 用户）
- 可选模块后做（满足 20% 特殊需求）
- 模块化设计（可插拔）
```

## 💡 关键决策理由

### 为什么分阶段？
```
一次性交付的风险：
- 开发周期长（6个月）
- 需求变化风险高
- 用户等不及
- 投入产出比低（做了很多用户不用的功能）

分阶段交付的优势：
- 快速验证（2个月看到成果）
- 降低风险（每阶段独立验收）
- 用户反馈（Phase 1 用户反馈指导 Phase 2）
- 灵活调整（Phase 2 可以根据市场调整）
```

### 为什么 Phase 1 只做财务核算？
```
理由：
1. 财务合规是刚需（必须做）
2. 财务核算是基础（Phase 2 依赖 Phase 1 数据）
3. 用户价值明确（替代 Excel）
4. 技术风险低（CRUD 为主）
5. 2个月可交付（快速验证）
```

### 为什么不做库存管理？
```
理由：
1. 只有 20% 企业需要（制造业）
2. 复杂度高（成本核算方法多样）
3. 不影响 80% 用户使用
4. 可以作为可选模块后续开发
```
