# 加权多视角产品审查（飞牛经营系统）

## 0. 为何做一次「纠正式」再审查

此前版本将**财务、产品、Boss、阿米巴**四视角**并列、篇幅接近**，容易隐含「四者同等重要」的评审假设。对**经营型产品**而言，这往往**不对**：数字与流程必须首先回答**人心与组织能否持续挑战高目标**（哲学与现场），其次才是账簿、界面与管理层报表。

本次再审查采用**显式权重**，结论按权重合成，而非四格平权投票。

---

## 1. 加权模型（评审口径）

| 视角 | 权重 | 说明 |
|------|------|------|
| **稻盛和夫 / 阿米巴式经营哲学与现场** | **40%** | 数字是否服务「提高心性、拓展经营」；是否促进透明与改善而非控人；系统与「单位时间附加值」「使命」的边界。 |
| **会计 / 财务** | **20%** | 可核对性、科目与事实、应收应付与经营事实的口径、可审计边界。 |
| **Boss / 管理层** | **20%** | 决策摘要、风险可见性、例会/复盘是否够用（文面「320%」视为笔误，本稿按 **20%** 计入，与财务、产品合计 100%；若贵司本意是 Boss 30%，则相应下调另三维各约 3.3% 并重算）。 |
| **产品 / 体验与闭环** | **20%** | 信息架构、主链路、异常与空态、与领域模型一致性。 |

**合成方式（建议）**：各视角独立打分（如 0～10），**加权求和**得到「经营就绪度」粗分；P0 问题仍具一票否决性质，不因稻盛权重高而下调安全类优先级。

---

## 2. 总判断（加权后 5～8 行）

在 **40% 稻盛维度**下，当前产品**最强**的是：项目级收支结构与预算—实际刷新，已能支撑**「用数字开一场诚实的经营对话」**的雏形。  
**最弱**的是：**责任单元与哲学边界未产品化**——系统既不能替巴长承担「挑战高目标」的意志，也未提供「单位时间附加值」或组织分账，阿米巴会议仍大量依赖线下切分与定性。

在 **财务 20% + Boss 20%** 下：账簿级完备性与对外披露**未承诺**；管理层仪表盘**覆盖面够**但 drill-down 与责任主体仍弱。  
在 **产品 20%** 下：技术栈与模块边界清晰，Demo 闭环可跑。

**加权总评**：作为 **「哲学先行、数字跟随」** 的经营 Demo **方向正确**；作为 **「平权四角色」** 的传统软件评审对象则**容易误判重心**。尚不宜作为唯一经营真相源上线；若只排一期迭代，建议 **P0 安全 + 阿米巴叙事与责任单元路线图** 同列，而非只做报表。

---

## 3. 稻盛和夫 / 阿米巴式经营视角（权重 40%，主章节）

### 3.1 角色定义（本视角查什么）

- **提高心性、拓展经营**：界面与指标是否在暗示「惟数字论」或排名羞辱，还是导向**改善与感谢**。
- **销售最大化、费用最小化、时间最小化**：现有「收入 / 成本 / 利润」是否可落到**谁、在哪个时段、为哪类客户**创造了附加值；是否缺「单位时间」维度。
- **透明与现场**：数字能否在例会中被**现场人员读懂并承诺行动**；黑箱聚合是否反而削弱信任。
- **哲学边界**：系统是否错误承担**定价权、人事评价、使命宣言**的替代表达。

### 3.2 正面反馈（可延续，与代码挂钩）

- **项目维 P&amp;L 与成本结构**（[`ProjectAppService`](../backend/src/main/java/com/profit/application/ProjectAppService.java)）：便于把「这一摊生意」当作**临时经营体**讨论，贴近「小集体」算账习惯。
- **预算 vs 实际**（[`BudgetAppService.refreshActuals`](../backend/src/main/java/com/profit/application/BudgetAppService.java)）：支撑**计划—执行—对照—反省**循环，与「每月销售与费用目标」式经营节奏相容。
- **收支事实 `fact_event` 带状态**：为「承认过去记录有误并改正」留有余地，与**极度认真、天天反省**的文化相容，而非只能硬删历史。

### 3.3 边界确认（系统不负责什么）

- **不计量「单位时间附加值」、不内置巴长任免、不做内部买卖价」**：当前模型无 `org_unit` / 工时 / 内部结算价；这些若强行用报表替代，会**扭曲**阿米巴本意。
- **不输出道德评判**：排行榜（如客户分析 [`AnalysisController`](../backend/src/main/java/com/profit/controller/AnalysisController.java)）若缺少**目的说明**（为何排名、用于何种改善），易滑向控人工具；需在文案与流程上反复强调**用于客户价值与费用结构改善**。

### 3.4 本视角下的主要缺口（占 40% 权重的结论落点）

| 缺口 | 对经营哲学的影响 |
|------|------------------|
| 无责任单元 / 巴 | 无法把「我的挑战」与数字绑定，**挑战高目标**易落空谈。 |
| 仪表盘全公司聚合为主 | 利于 Boss 一眼，弱于**现场体感**；与 40% 权重下的期望有张力，需「从项目/客户钻取」补偿。 |
| 安全与信任（P0） | 数据可被注入或篡改时，**透明即谎言**，直接伤害「以心为本」的经营基础。 |

## 4. 会计 / 财务视角（权重 20%）

### 角色定义

可核对凭证链、科目与 `fact_event`、应收/应付与经营事实关系、预算映射是否可辩护。

### 正面反馈

领域拆分清晰；`status='valid'` 参与聚合（[`DashboardService`](../backend/src/main/java/com/profit/dashboard/DashboardService.java)）有利于过账/作废模型延伸。

### 边界确认

不承诺准则与税务；单账号与内存会话（[`TokenStore`](../backend/src/main/java/com/profit/auth/TokenStore.java)）不满足职责分离；JdbcTemplate 直查与领域服务并存时需约定**哪条为账簿真相**。

---

## 5. Boss / 管理层视角（权重 20%）

### 角色定义

首页能否回答赚多少、本月、应收应付与逾期、客户贡献；风险能否关联到项目/客户/合同。

### 正面反馈

[`DashboardSummary`](../backend/src/main/java/com/profit/dashboard/DashboardSummary.java) 覆盖全公司摘要与客户 Top，适合周会初稿。

### 边界确认

聚合快照非现金流预测；无多组织时多事业部考核需线下或二期建模。

---

## 6. 产品 / 体验视角（权重 20%）

### 角色定义

主链路、异常与空态、信息架构与领域一致性。

### 正面反馈

Vue 3 + Element Plus + 统一 `http`；路由与登录壳（[`frontend/src/router`](../frontend/src/router/index.ts)）就绪。

### 边界确认

不替代财务口径；协作与审批未承诺则不在本阶段苛责。

## 7. 问题清单（优先级 + 加权主导视角）

「主导视角」表示：**在加权评审中更应由该视角推动整改叙事**（不等同于唯一 owner）。

| ID | 描述 | 优先级 | 主导视角（加权） | 证据 / 位置 |
|----|------|--------|------------------|-------------|
| P0-SEC-1 | 客户排名日期参数拼入 SQL，**注入与篡改风险** | P0 | **稻盛 40%**（破坏信任根基）+ 财务 | [`AnalysisController`](../backend/src/main/java/com/profit/controller/AnalysisController.java) |
| P0-AUTH-1 | 内存 Token、单账号、无审计 | P0 | 财务 + **稻盛**（透明须以真实为前提） | [`TokenStore`](../backend/src/main/java/com/profit/auth/TokenStore.java)，[`application.yml`](../backend/src/main/resources/application.yml) |
| P1-DATA-1 | `fact_event` 与应收/应付口径未显性化 | P1 | 财务 + **稻盛**（现场对账扯皮伤害一体感） | 领域设计 |
| P1-FE-1 | 全表聚合与性能/一致性风险 | P1 | Boss + 产品 + **稻盛**（例会卡顿削弱反省节奏） | [`DashboardService`](../backend/src/main/java/com/profit/dashboard/DashboardService.java) 等 |
| P2-AMB-1 | 无组织/巴单元维度 | P2 | **稻盛 40%**（核心缺口） | 数据模型 |
| P2-DOC-1 | 口径文档与运行行为未版本绑定 | P2 | 财务 + 产品 | [`docs/`](.) |

**责任方（首轮）**：P0 产研 + 安全；P1 财务主导口径 + 产品文案；P2-AMB-1 需管理层与产研共定「是否做责任单元」的产品决策后再排期。
